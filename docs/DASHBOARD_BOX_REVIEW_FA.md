# بررسی باکس‌های مرکز فرمان

تاریخ: ۲۰۲۶/۱۰/۳۱ — ۱۴۰۵/۰۸/۰۹

دامنه: ۱۶ کارت داخل `#novaControlCenterGrid` در فایل ارسالی کاربر و سورس نسخهٔ ۲.۶.۰. این گزارش بررسی سورس است؛ صحت اعداد حساب آنلاین از روی HTML قابل اثبات نیست. در زمان بررسی API محلی پورت ۳۰۰۲ در دسترس نبود و نشست احراز هویت دیتابیس آنلاین در اختیار بررسی نبود. هیچ داده یا بخشی حذف نشده و انتشار انجام نشده است.

## معیار ضرورت

هدف کاربر دیدن کارهای روز، برنامه‌ریزی هفته، حفظ روتین، مرور پروژه‌ها و بانک آیتم‌ها و تغییر برنامه در شرایط ناگهانی است. وجود جدول یا API به‌تنهایی دلیل نیاز به یک باکس مستقل در مرکز فرمان نیست. خالی‌بودن یک باکس نیز مجوز حذف داده‌های آن نیست.

## یافته‌های قطعی دربارهٔ آمار

۱. در HTML اولیه درصدها، وضعیت‌ها و ردیف‌های نمونه وجود دارند؛ مانند ۸۸٪ برای کارها، ۷۰٪ برای پروژه‌ها و ۲۰ عادت فعال. `hydrateModuleCards()` بعد از بارگذاری legacy تعدادی را با دادهٔ API جایگزین می‌کند، اما وجود مقدار واقعی پس از بارگذاری، امن‌بودن وضعیت اولیه یا خطای شبکه را تضمین نمی‌کند.

۲. هم `genericModuleFromItems()` در کلاینت و هم `moduleSummary()` در سرور، فهرست خالی را صفر درصد و «نیازمند توجه» اعلام می‌کنند. این قضاوت از دادهٔ عملکرد حاصل نشده؛ باید «موردی ثبت نشده» نمایش داده شود.

۳. `novaSyncControlCenter()` چند KPI را از DOM بخش‌های دیگر کپی می‌کند. این روش به ترتیب بازکردن صفحه‌ها وابسته است؛ دریافت‌نشدن داده، صفر واقعی نیست و دادهٔ بازهٔ قبلی نباید با عنوان امروز/این هفته نشان داده شود.

۴. `loadV115Schedule()` و `loadV117()` هنگام خطای API از fallback استفاده می‌کنند. fallback تقویم در نبود دادهٔ محلی، رویدادهای `demo1` تا `demo3` می‌سازد؛ fallback هدف‌ها هدف‌های ثابت می‌سازد. بنابراین صرفاً سالم‌بودن تنظیمات PostgreSQL سرور برای حذف آمار نمونهٔ رابط کافی نیست. مسیرهای نمونهٔ دیگری نیز در `v1111Load()` برای معنویت وجود دارند؛ نباید هنگام اتصال مجدد باکس‌ها به منبع جدید از این fallbackها استفاده شود.

۵. ۲۳ کار و ۸ پروژه در HTML ارسالی نتیجهٔ جایگزینی با داده‌های bootstrap به نظر می‌رسند، نه همان اعداد ثابت اولیه؛ اما واقعی یا آزمایشی بودن خود رکوردها، مالکیت حساب و کامل‌بودن تعداد از روی HTML قابل تأیید نیست. هیچ رکوردی نباید بر اساس نام، UUID یا ظن به آزمایشی‌بودن پاک شود.

## شکل پیشنهادی مرکز فرمان

هشت خلاصهٔ اصلی کافی است: کارهای روز، پروژه‌ها، روتین‌ها، جلسات، تقویم، در انتظار، مرور/برنامهٔ هفته و بانک آیتم‌ها. هرکدام باید یک تصمیم یا اقدام مشخص فراهم کند و خلاصهٔ مشابه بالای صفحه با آن ادغام شود. هدف‌ها زیر پروژه‌ها/مرور، معنویت و سلامت زیر روتین‌ها، مناسبت‌ها زیر تقویم و یادگیری در تحصیل باقی بمانند. مالی و روابط بر اساس استفادهٔ واقعی کاربر اختیاری باشند. ثبت سریع به عنوان باکس مستقل کنار گذاشته شود.

این پیشنهاد به‌معنی پیاده‌سازی زمان‌بندی خودکار نیست؛ تغییر برنامه در شرایط ناگهانی هنوز نیازمند طراحی و پیاده‌سازی مستقل است.

## معیار اصلاح و تأیید بعدی

- آمار از پاسخ API همان حساب و بازهٔ صریح بیاید؛ انتقال متن از صفحهٔ دیگر کنار گذاشته شود.
- قبل از دریافت: «در حال دریافت»؛ در خطا: «دریافت نشد» و تلاش دوباره؛ در پاسخ موفق خالی: «موردی ثبت نشده». صفر فقط نتیجهٔ پاسخ موفق باشد.
- دادهٔ نمونه هنگام شکست درخواست تولید نشود. عددهای قدیمی با عنوان جدید نمایش داده نشوند.
- ردیف‌های خلاصه دکمهٔ «ویرایش این مورد» نگیرند؛ فقط رکورد واقعی قابل ویرایش باشد.
- نوع داده و وضعیت با همان صفحهٔ مقصد مشترک باشد؛ مثلاً مرور از reviews و افراد از relationships خوانده شوند.
- هیچ جدول یا رکوردی برای حذف باکس پاک نشود و بانک پایه بدون تصمیم مستقل به دیتابیس وارد نشود.
- بعد از اصلاح، اولین ورود، تغییر تاریخ، ثبت تغییر، خطای شبکه و حساب خالی بررسی شوند؛ سپس محیط آنلاین با `/api/health` دارای storage برابر PostgreSQL و نشست همان کاربر بررسی شود. تست محلی جای این تأیید را نمی‌گیرد.

- `public/assets/integrated-tools.js`: مقصدهای فعلی سلامت، مناسبت‌ها، حوزه‌ها و منابع یادگیری.
