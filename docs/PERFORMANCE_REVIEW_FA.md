# بررسی سرعت و عملکرد NOAVA

تاریخ بررسی: ۲۰۲۶/۱۰/۳۱ — ۱۴۰۵/۰۸/۰۹. سنجش محلی روی نسخهٔ پایهٔ ۲.۶.۰، در جریان آماده‌سازی اصلاحات نسخهٔ ۲.۷.۰ انجام شده است.

## سرعت سایت به چه چیزهایی بستگی دارد؟

| عامل | اثر روی تجربه | روش بررسی در این پروژه |
|---|---|---|
| شبکه و محل سرور | DNS، TLS، فاصلهٔ جغرافیایی، تأخیر و پهنای باند | مقایسه با محدودیت شبکه؛ تست لوکال زمان اینترنت واقعی را اثبات نمی‌کند |
| سرور و دیتابیس | زمان اولین پاسخ، تعداد کوئری، اتصال و کار تکراری | بررسی API، مسیر همگام‌سازی و جداسازی حساب‌ها؛ زمان PostgreSQL آنلاین هنوز اندازه‌گیری نشده |
| حجم فایل و تعداد درخواست | تأخیر نمایش و مصرف اینترنت | اندازهٔ HTML، JS، CSS، فونت، بانک و فشرده‌سازی |
| وابستگی‌های بیرونی | تأخیر یا شکست CDN و فونت | ثبت درخواست‌های مرورگر و حذف وابستگی فونت به میزبان بیرونی |
| جاوااسکریپت و DOM | توقف رشتهٔ اصلی، کندی کلیک و فرم | مشاهدهٔ long task و مرورگر با پردازندهٔ چهار برابر کندتر |
| ترتیب استایل و فضای محتوا | ظاهر اولیهٔ اشتباه و جهش صفحه | ردیابی منابع layout shift و بررسی اندازهٔ سربرگ، منو و کنترل تاریخ |
| کش و کار پس‌زمینه | سرعت مراجعهٔ بعد، درخواست و پردازش اضافه | بررسی کش مرورگر/سرویس‌ورکر، TTL، اعلان و درخواست‌های تکراری |

معیارهای رسمی تجربهٔ کاربر شامل LCP برای نمایش محتوای اصلی، INP برای پاسخ‌گویی به تعامل و CLS برای ثبات چیدمان‌اند. اهداف خوب به‌ترتیب ۲٫۵ ثانیه، ۲۰۰ میلی‌ثانیه و ۰٫۱، در صدک ۷۵ بازدیدهای واقعی هستند. اندازه‌گیری آزمایشگاهی محلی جای دادهٔ کاربران واقعی را نمی‌گیرد. [راهنمای رسمی Web Vitals](https://web.dev/articles/vitals)، [بهینه‌سازی LCP](https://web.dev/articles/optimize-lcp)، [بهینه‌سازی INP](https://web.dev/articles/optimize-inp).

## مشکل‌های پیدا‌شده و اصلاح‌ها

۱. درخواست خودکار `/favicon.ico` به fallback صفحه می‌رسید و کل HTML، حدود ۶۲۵ کیلوبایت، دوباره دانلود می‌شد. آیکون SVG واقعی اضافه شد؛ مسیر فایل ناموجود و مسیر API ناموجود ۴۰۴ می‌دهند و fallback فقط برای مسیر صفحه باقی است.

۲. HTML و فایل‌های public بدون کوچک‌سازی منتشر می‌شدند. مرحلهٔ ساخت، CSS و JS را کوچک می‌کند و محل و ترتیب اصلی کد/استایل را نگه می‌دارد. نسخه‌های gzip و Brotli برای خروجی استاتیک ساخته می‌شوند. سرور مستقل آن‌ها را با `Accept-Encoding` و `Vary` صحیح ارائه می‌دهد. Vercel سیاست فشرده‌سازی خودش را دارد؛ نتایج سرور مستقل را نباید به‌عنوان بهبود تأییدشدهٔ Vercel معرفی کرد.

۳. اسکریپت‌های تکمیلی انتهای صفحه هنگام parse اجرا می‌شدند. اکنون دانلود موازی و اجرای `defer` با ترتیب مشخص دارند. پس از آماده‌شدن فایل‌ها، مقصد فعلی دوباره آماده می‌شود تا رفتن زودهنگام به یک صفحه در اینترنت کند به صفحهٔ خالی منجر نشود.

۴. فونت از stylesheet بیرونی و چند وزن مجزا دریافت می‌شد. اکنون یک فایل متغیر Vazirmatn v33.003، به حجم ۱۱۱۱۵۲ بایت، با مجوز OFL در خود سایت وجود دارد. فونت پس از دریافت اولیهٔ داشبورد یا هنگام نمایش ورود فعال می‌شود؛ متن در این مدت خوانا است. [منبع رسمی فونت](https://github.com/rastikerdar/vazirmatn/tree/v33.003/fonts/webfonts). مجوز در `public/fonts/OFL-Vazirmatn.txt` نگه داشته شده است.

۵. سربرگ و منو پس از نمایش اولیه استایل نهایی می‌گرفتند و جابه‌جا می‌شدند. استایل‌های کوچک و ضروریِ پوسته، تاریخ و سربرگ به head رفتند. وضعیت بازبودن گروه‌های منو و جمع‌شدن sidebar قبل از نمایش محتوای اصلی بازیابی می‌شود. برای کنترل تاریخ داشبورد، فضای هم‌اندازه از ابتدا رزرو و با کنترل واقعی جایگزین می‌شود.

۶. auth و bootstrap دو درخواست جداگانهٔ health می‌فرستادند. اکنون یک Promise مشترک مصرف می‌کنند. badge معنوی نیز به‌جای دریافت مجدد هنگام هر جابه‌جایی، از کش کوتاه‌مدت و invalidation تغییرات استفاده می‌کند.

۷. کتاب‌خوانی در پس‌زمینه همهٔ کتاب‌ها و تاریخچهٔ جلسه‌ها را دریافت می‌کرد. مسیر کم‌حجم `/api/reading/reminders` فقط اطلاعات لازمِ کتاب‌های دارای یادآور و جمع امروز را می‌دهد. تاریخچه فقط هنگام بازبودن صفحهٔ کتاب‌خوانی دریافت می‌شود. محاسبهٔ جمع زمان هر کتاب نیز از فیلترکردن همهٔ جلسه‌ها برای تک‌تک کتاب‌ها به یک پیمایش تبدیل شده است.

۸. `getV11Canonical` در هر خواندن، همگام‌سازی legacy به مدل اصلی را با چندین حلقه و کوئری تکرار می‌کرد. اکنون فقط همان همگام‌سازی برای هر حساب تجمیع می‌شود و حداکثر ۱۵ ثانیه اعتبار دارد. تغییر موفق همان حساب، اعتبار را باطل می‌کند؛ خطا کش نمی‌شود و اندازهٔ حافظه محدود است. پاسخ خصوصی API کش مشترک نمی‌شود و خواندن واقعی داده همچنان انجام می‌شود. در چند نمونهٔ serverless، تغییر نمونهٔ دیگر ممکن است تا پایان این ۱۵ ثانیه برای همگام‌سازی منابع قدیمی منتظر بماند؛ این کش، تضمین تراکنش یا کش بین نمونه‌ها نیست.

۹. بانک پایه نزدیک ۴٫۹۱ مگابایت است؛ نسخهٔ gzip آن حدود ۲۴۴ کیلوبایت می‌شود. دریافت تنبل، یک‌بار دریافت فایل و صفحه‌بندی ۵۰ ردیفی موجود حفظ و در مرورگر بررسی شدند.

## روش اندازه‌گیری

- خروجی build، سرور محلی جداگانه روی ۳۰۳۳ و store آزمایشی جدا از دادهٔ معمول کاربر.
- Edge headless، سه بار بارگذاری سرد دسکتاپ در عرض ۱۲۸۰ و سه بار موبایل در عرض ۳۹۰؛ یک بار مراجعهٔ گرم برای مشاهدهٔ کش.
- دسکتاپ: تأخیر ۲۰ میلی‌ثانیه و دانلود ۱٫۲۵ مگابایت بر ثانیه؛ موبایل: تأخیر ۱۵۰ میلی‌ثانیه، دانلود ۲۰۰ کیلوبایت بر ثانیه و CPU چهار برابر کندتر.
- کش در تست سرد خاموش و service worker bypass است. اعداد جمع‌بندی، میانهٔ سه تکرارند.
- `dataReadyMs` زمان مشاهدهٔ پاسخ داشبورد در مرورگر است؛ `fcp` و `lcp` از PerformanceObserver می‌آیند. دادهٔ LCP تا پنجرهٔ مشاهدهٔ آزمون است، نه دادهٔ واقعی همهٔ عمر بازدید.
- مقدار `cls` در فایل خام، مجموع تغییرهای بدون تعامل در پنجرهٔ مشاهده است؛ پیاده‌سازی کامل session window رسمی CLS نیست و نباید نمرهٔ رسمی Core Web Vitals نامیده شود.
- `blockingMs` مجموع قسمت بیشتر از ۵۰ میلی‌ثانیهٔ long taskهاست؛ INP واقعی اندازه‌گیری نشده است. زمان آماده‌شدن صفحهٔ آمار در این اسکریپت نیز INP نیست.
- اندازهٔ gzip از فایل خروجی و negotiation هدر سرور تأیید شده است. واسط محیط مرورگر ممکن است پاسخ را پیش از تحویل باز کند؛ برای حجم روی شبکه صرفاً به `encodedBodySize` آن اتکا نشده است.
- دادهٔ خام قبل/بعد در `.local/performance-before.json` و `.local/performance-after.json` است و در Git یا انتشار قرار نمی‌گیرد.

## نتیجهٔ اندازه‌گیری نهایی

میانهٔ سه اجرای سرد در هر حالت، با همان محدودیت شبکه و CPU:

| سنجه | قبل | بعد | تفسیر |
|---|---:|---:|---|
| آماده‌شدن دادهٔ داشبورد، دسکتاپ | ۷۰۹ ms | ۵۸۷ ms | حدود ۱۷٪ کمتر |
| اولین نمایش محتوا، دسکتاپ | ۵۳۲ ms | ۳۶۸ ms | حدود ۳۱٪ کمتر |
| پایان load، دسکتاپ | ۱۵۰۱ ms | ۱۰۱۱ ms | حدود ۳۳٪ کمتر |
| آماده‌شدن دادهٔ داشبورد، موبایل محدودشده | ۳۲۱۶ ms | ۳۱۹۵ ms | تقریباً ثابت؛ بهبود قطعی قابل توجه ادعا نمی‌شود |
| نمایش محتوای اصلی، موبایل محدودشده | ۲۲۰۴ ms | ۲۲۰۸ ms | تقریباً ثابت |
| مجموع جابه‌جایی بدون تعامل، دسکتاپ | ۰٫۱۵۷ | ۰٫۰۵۳ | حدود ۶۶٪ کمتر؛ نمرهٔ رسمی CLS کاربران نیست |
| مجموع جابه‌جایی بدون تعامل، موبایل | ۰٫۱۸۵ | ۰٫۰۳۶ | حدود ۸۱٪ کمتر |
| زمان مسدودکنندهٔ long taskها، موبایل | ۳۷۲ ms | ۲۸۳ ms | حدود ۲۴٪ کمتر؛ INP نیست |

تعداد نمونه‌ها کم است و این درصدها مربوط به همین آزمایش‌اند. نتیجهٔ مهم موبایل، ثبات بیشتر چیدمان و کاهش کار مسدودکننده است؛ سرعت دریافت اولیهٔ داده تقریباً همان مانده است. اجرای گرم دسکتاپ فقط یک نمونه دارد و برای نتیجه‌گیری درصدی استفاده نشده است.

HTML آمادهٔ انتشار از ۶۲۴۵۹۸ به حدود ۵۹۳۴۹۲ بایت رسیده است. کاهش اصلی درخواست بیهودهٔ آیکون، کاهش درخواست تکراری و تحویل فشرده است؛ حذف قابلیت یا داده برای رسیدن به عدد کوچک‌تر انجام نشده است. gzip خروجی فعلی HTML حدود ۱۳۴ کیلوبایت است. بانک پایه ۴۹۰۹۶۹۹ بایت و نسخهٔ gzip آن ۲۴۳۵۸۶ بایت است.

در آزمون تحویل، gzip و Brotli به همان محتوا باز شدند، فونت و آیکون واقعی پاسخ گرفتند، فایل/API ناموجود ۴۰۴ بود و لینک داخلی صفحه همچنان HTML گرفت. آزمون مرورگر همچنین عدم دریافت اولیهٔ بانک، صفحه‌بندی ۵۰ ردیفی، ویرایش بانک، تقویم، کتاب‌خوانی، آمار، سربرگ و احراز هویت را بررسی کرد.

## محدودیت‌ها و موارد باقی‌مانده

- HTML حدود ۵۹۳ کیلوبایتِ بازنشده دارد و هنوز بزرگ است؛ انتقال قابلیت‌های قدیمی به ماژول‌های واقعاً تنبل، تغییر معماری جداگانه با آزمون همهٔ فرم‌ها می‌خواهد. جداکردن یا تجمیع گستردهٔ کد و CSS در این بررسی، بارگذاری سرد موبایل را بدتر کرد؛ نسخهٔ کم‌حجم‌تر صرفاً به‌خاطر عدد حجم انتخاب نشد.
- تعداد عناصر اولیه حدود سه هزار است و چند نمای قدیمی به‌صورت مخفی در DOM هستند. صفحه‌بندی بانک جلوی ساخت هم‌زمان هزاران ردیف دیگر را می‌گیرد.
- خواندن مدل کامل برای برخی APIها، حجم دادهٔ حساب‌های بزرگ و زمان کوئری PostgreSQL آنلاین هنوز باید در محیط واقعی با نشست مجاز و بدون تغییر داده بررسی شوند. سرعت memory در لوکال، سرعت PostgreSQL نیست.
- نمرهٔ Lighthouse، INP کاربران واقعی، صدک ۷۵، cold start واقعی Vercel، فاصلهٔ دیتاسنتر و شرایط اینترنت کاربر از این آزمون نتیجه‌گیری نشده‌اند.
- در زمان انجام این سنجش‌ها هیچ دادهٔ واقعی حذف، هیچ store آزمایشی وارد دیتابیس، و هیچ push یا انتشار انجام نشده بود.

## اجرای بررسی‌ها

`npm.cmd run build` و `npm.cmd run qa`، سپس `scripts/check-delivery.mjs` برای تحویل فایل‌ها، `scripts/check-performance-browser.mjs` برای بارگذاری اولیه/بانک/تقویم و آزمون‌های مرورگر کتاب‌خوانی، آمار، سربرگ و ورود.

`scripts/measure-performance-browser.mjs` برای ثبت سنجش قبل/بعد و `scripts/measure-layout-shifts-browser.mjs` برای یافتن عناصر جابه‌جاشده است. آزمون‌های قابلیت‌ها باید روی store جداگانه اجرا شوند و هنگام اندازه‌گیری سرعت نباید هم‌زمان همان تب مرورگر را کنترل کنند.
